# Аудит безопасности Android-патчсета

Дата: 2026-11-10. Исходная очередь: 331 патч поверх Telegram Android 13.2.1 (7291).

Это статический аудит кода форка и вызывающих stock-хуков, не утверждение об отсутствии остальных уязвимостей. Исходные находки не проверялись эксплуатацией. P1 — первая очередь исправлений, P2 — следующая. Статусы ниже меняются только по результатам реализации и проверки; сборка не заменяет ручную проверку.

## Реализация и совместимость

- `TeleAccounts`: владелец слота — user ID + test/prod, поколения callbacks, очистка таблиц/KV/кешей/скриптов при logout и смене владельца. При первом обновлении активный аккаунт сохраняет существующие архивы; прежние разрешения и storage скриптов сбрасываются, неактивные слоты очищаются. Достоверно восстановить владельца старых slot-only архивов невозможно: ранее унаследованные активным слотом записи автоматически не различаются. Для них нужна ручная очистка; обещания ретроактивной атрибуции нет.
- Источники скриптов привязаны SHA-256 к содержимому и location. Импорт/замена/смена каталога отзывают доверие; неизменённый rescan не требует повторного consent.
- `ScriptReplies`: ответы принадлежат pending runtime, одноразовые; неизвестные token не создают записи. Stop/unregister отменяет ожидание.
- Streamer mode имеет приоритет над разрешениями скриншотов в отдельных окнах.
- Last seen rollback хранит полный TL-набор InputPrivacyRule и owner/backend в durable journal; частичный набор не отправляется, single-flight не допускает перезаписи исходника.
- StarsLock закрепляет владельца глобального пароля. Legacy verifier без владельца требует успешного ввода локального пароля перед привязкой; другой аккаунт не разрешает recovery. Отсутствующий владелец не понижает защиту до countdown.
- Hidden-word regex имеет общий бюджет 8 мс/100000 чтений на классификацию; исчерпание и StackOverflowError дают fail-open.
- Notices ограничены стороной 16384 и площадью 32 мегапикселя; decode sampling учитывает обе стороны.
- Update tag ограничен форматом версии и длиной 96; target и .part проверяют canonical parent. Существующая докачка сохраняется.

### Ручная приёмка на emulator-5554

1. В scripts включить безопасный тестовый скрипт, затем импортировать замену с тем же именем: скрипт выключен, прежние permissions отозваны; после явного enable/consent снова работает. Повторить с неизменённым файлом.
2. С двумя тестовыми аккаунтами: разрешить notification interceptor только A, отправить обычное сообщение B в предоставленные тестовые личные сообщения/чат. Скрипт A не получает текст B; штатное уведомление B остаётся. Нужны оба аккаунта, один аккаунт эту границу не проверяет.
3. Сохранить заведомо тестовый черновик и удалённое сообщение A, выйти из A, войти другим тестовым пользователем в тот же слот: архивы, черновики и script permissions A недоступны. Не выходить из единственного важного аккаунта ради теста.
4. Streamer mode on: открыть тестовое исчезающее фото/видео и одноразовый voice player, проверить FLAG_SECURE/захват; off — проверить существующие разрешения screenshots. Не использовать приватные медиа.
5. StarsLock: пароль установлен владельцем A; на B forgot password не использует 2FA B для глобального сброса. При отсутствующем A сброс не разрешён; правильный локальный пароль остаётся рабочим. Никаких реальных платежей.
6. Last seen: на тестовом аккаунте проверить полный набор исключений до/после peek и холодного рестарта. Отдельно сетевой сбой и повторный peek не должны затирать rollback. Не менять privacy основного аккаунта для испытания.
7. Hidden words: обычное literal/regex правило фильтрует сообщение в test chat, неблагоприятное regex не зависает. Отключение фильтра возвращает stock-отрисовку.


## SEC-01: уведомления разных аккаунтов

`src/main/java/org/telegram/messenger/NotificationsController.java:1091–1103` передаёт текст, chatId и fromId в `tele/scripting/ScriptNotifications.kt:41–63`, но не account. Глобальный список runtimes не фильтруется по владельцу.

Условия: включённый скрипт A с interceptNotification и входящее сообщение B. Скрипт получает текст B и может подавить уведомление. Fetch для самой утечки не требуется.

Исправление: передавать account, фильтровать runtime до передачи payload. Проверка: runtime A не вызывается для B; B получает своё событие; остановленный runtime не получает события.

## SEC-02: доверие при замене скрипта

`TeleScriptsActivity.kt:324–340,386–401` после импорта вызывает refresh; `Scripts.kt:69–107,358–372` повторно запускает изменённый источник с прежними enabled/grants. `ScriptStore.kt:15–40` связывает доверие только с id. Сообщение UI обещает, что импорт выключен. Удаление и смена папки не отзывают доверие.

Условия: ранее одобрен одноимённый скрипт, пользователь импортирует замену или выбирает другой каталог. Новый код наследует возможности без нового consent.

Исправление: новый/заменённый источник выключен, разрешения отозваны; смена источника не переносит доверие; удаление очищает approvals. Проверка: замена, удаление/повторный импорт, смена папки не запускают код; явное повторное одобрение работает.

## SEC-03: переиспользование слота

`MessagesController.java:16271–16305` не очищает fork-архивы и scripting state. Общая `tele.db` (`TeleDatabaseHelper.kt:60–69,308–317,714`) и `tele_scripts_N` (`ScriptStore.kt:15–59`) используют номер слота, а не стабильного владельца.

Условия: A выходит, B входит в тот же слот без очистки данных приложения. B видит сообщения/черновики A; скрипты A могут выполнять ранее разрешённые RPC от имени B; storage/logs также переходят B.

Исправление: централизованная очистка fork-данных/кешей и остановка runtimes при logout; owner guard перед чтением и запуском. Старые slot-only approvals нельзя автоматически передавать новому пользователю. Учесть отложенные callbacks и записи.

Проверка: смена владельца очищает архивы, черновики, grants, storage, per-chat KV; поздний callback A не пишет состояние B; соседний аккаунт не затронут.

## SEC-04: защита секретных окон

`SecretMediaViewer.java:1568–1576` снимает FLAG_SECURE при STREAMER_MODE; `SecretVoicePlayer.java:242–244` не ставит флаг. Это противоположно `FlagSecureReason.java:67–70`. Основное окно Activity не защищает отдельные окна.

Условия: streamer mode, открытие исчезающего медиа, захват экрана. Содержимое может попасть в трансляцию.

Исправление: streamer mode принудительно включает защиту до обработки разрешений скриншотов. Проверка: streamer on защищает отдельные окна независимо от NEVER_BLOCK_SCREENSHOTS; off сохраняет существующую семантику.

## SEC-05: verdict endpoints

`jni/tele_script_jni.cpp:200–203` публикует __teleHost. `ScriptRuntime.kt:422–456` принимает drop/notification/link verdict без grant и identity проверки. `ScriptLinks.kt:19–37`, `ScriptNotifications.kt:18–36`, `ScriptDrops.kt` сохраняют ответы для любых token.

Условия: любой включённый недоверенный скрипт, даже без grants. Подтверждённый эффект: неограниченное накопление JVM-объектов вне QuickJS quota. Подмена действующего ответа возможна при гонке; гарантированный перехват не утверждается. Предварительный ответ сам по себе будущий waiter не будит.

Исправление: pending request привязан к runtime; grant и владельца проверять в host; неизвестные/просроченные token отвергать, ответ принимать один раз; cleanup при stop.

Проверка: чужой, повторный, просроченный и неизвестный ответ отвергаются без накопления; разрешённый владелец отвечает; timeout/stop снимают pending.

## SEC-06: восстановление приватности

`LastSeenPeek.kt:96–105,262–270,299–301` молча пропускает deny-user без объекта в memory cache, отправляет неполные правила и удаляет journal. `TeleHooks.kt:45` запускает восстановление до гарантированного прогрева пользователей.

Условия: pending journal после прерывания peek, исходные allow_all/allow_contacts с deny exceptions, исключённый пользователь не в cache. Запрет теряется на сервере постоянно. Аналогичная потеря allow exceptions сужает доступ. Дополнительная гонка: второй peek перезаписывает journal первого (`61–62`), single-flight отсутствует.

Исправление: никогда не отправлять частичный rollback; хранить достаточные InputUser данные; сохранять journal до полного подтверждения; single-flight на аккаунт. Проверка: cold restore с исключениями, неразрешимый пользователь, повторный peek, ошибка сети и рестарт.

## SEC-07: общий StarsLock

`StarsLock.kt:320–345`, `StarsLockUi.kt:290–318`: общий verifier сбрасывается через selectedAccount; при отсутствии 2FA достаточно countdown.

Условия: доступ к разблокированному приложению, защищаемый аккаунт с 2FA и другой без 2FA. Пароль снимается глобально без секрета защищаемого владельца.

Исправление: закрепить стабильного владельца глобального lock/recovery или разделить lock по аккаунтам. Проверка: другой аккаунт не авторизует reset, правильный владелец с облачным паролем восстанавливает доступ; отсутствие владельца не понижает защиту до countdown.

## SEC-08: regex DoS

`PrivacyRules.kt:235–249,279–290` применяет пользовательские Java regex без бюджета. Вызовы из `ChatMessageCell.java:6260–6263` и `DialogCell.java:3470–3472` синхронны с UI. Проверка синтаксиса не ограничивает backtracking.

Условия: включённое неудачное regex-правило и неблагоприятный входящий текст. Отправитель контролирует текст, не правило. Возможны зависание UI/ANR и повторение при открытии.

Исправление: bounded regex matching; не оставлять бесконечно занятый worker. Использовать существующий guarded CharSequence-подход ChatSearch либо безопасный движок с сохранением понятной семантики. Проверка: дорогой match прерывается, обычные literal/regex правила корректны.

## SEC-09: bitmap notices

`TeleServerNotices.kt:451–456,509–522`: ограничен размер файла, но нет предела сторон/площади; sampling только по ширине.

Условия: контроль настроенного tele-server, notices включены, пользователь открывает запись. Узкое высокое изображение вызывает чрезмерное выделение памяти. runCatching не предотвращает попытку allocation; гарантированный crash не утверждается.

Исправление: лимиты обеих сторон/площади в Long до сохранения и decode; sampling по обеим сторонам и бюджету памяти. Проверка: oversized размеры отвергаются, допустимые изображения сохраняют корректный размер.

## SEC-10: путь обновления

`TeleUpdater.kt:184–201` принимает tag без запрета разделителей и строит путь `tele-${tag}.apk`; canonical containment отсутствует. SHA проверяется после записи.

Условия: контроль доверенного GitHub release feed и доступного файла, например компрометация публикации. Не обычный отправитель сообщения и не MITM без нарушения HTTPS. Возможна запись вне каталога обновлений в пределах прав приложения; суффиксы ограничены .apk/.apk.part. Произвольная перезапись любого файла и RCE не подтверждены.

Исправление: фиксированные локальные имена, независимые от tag, либо строгий allowlist и containment. Проверка: недоверенный tag не влияет на путь, штатный feed скачивается/возобновляется.

## Дополнительные наблюдения, не отдельные доказанные уязвимости

- Heap dump при явном экспорте может содержать сообщения и ключи; текущему приглашению не хватает предупреждения о чувствительности. Скрытая отправка не установлена.
- MTProto redaction скрывает password/auth/secret/phone/key/hash/token, но обычное поле code не скрывает. Журнал private, экспорт ручной; автоматическая эксфильтрация не доказана.
- Wallet JNI создаёт временные копии private key, UI использует текстовый EditText; самостоятельный доказанный канал эксфильтрации не установлен.
- Исключения internal-file проверки через подстроки tele_drafts/tele_docked требуют осторожности, но внешний share предварительно проверяет internal URI; достижимый обход не подтверждён.
- У MessageHistory нет явного TTL-фильтра, но достижимость для secret/disappearing edits не доказана.
- Обход StarsLock через settings backup не подтвердился: чувствительные настройки исключены при импорте/экспорте.

## Проверка и выпуск

Автоматические проверки должны упражнять поведение, а не совпадение текста исходников. Общая сборка выполняется после интеграции изменений, не параллельно редактированию. Патчи экспортируются только из коммитов дерева Telegram, .patch вручную не редактируются. UPSTREAM не меняется. Пользовательская ручная проверка — отдельно от статуса сборки.

Доступен emulator-5554; для согласованных проверок пользователь предоставил тестовый чат и канал. Не использовать реальные секреты/платежи. UI действия выполняет мейнтейнер; помощник — код, сборка, установка, логи и скриншоты.
