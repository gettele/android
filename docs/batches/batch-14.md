# Пачка 14 — хранилище tele.db: удалённые, закладки, лимиты GIF

## Назначение и границы

Этот документ задаёт последовательную реализацию строк пачки 14 из `docs/PATCHLIST.md`.

Пачка объединяет локальные данные, которые должны переживать перезапуск приложения.

Правило проекта: не менять схему Telegram и `LAST_DB_VERSION`; данные форка — только `tele_*` и `tele_kv`.

Правило проекта: каждый переключатель в `TeleConfig`, на странице настроек и в спецификации export/import.

Новые переключатели по умолчанию выключены; выключенное состояние обязано совпадать со стоком.

Код форка размещать в `tele/`; в stock-файлах оставлять только минимальные гейтированные вызовы.

Не редактировать `TLRPC.java` и экспортированные `.patch` вручную.

## Общие требования к БД

Работать с `TeleDatabaseHelper` через его штатную очередь/serial executor; UI не вызывает SQL синхронно.

Все операции привязывать к `currentAccount`; не захардкодить аккаунт 0.

Ключи и строки, содержащие account/dialog/topic/message, должны однозначно разделять аккаунты и контексты.

Предпочесть нормализованные `tele_*` таблицы для индексируемых/объёмных записей; `tele_kv` использовать только для компактных настроек/состояний.

Не сохранять целые Telegram-объекты, если существующие helpers уже дают безопасную сериализацию и восстановление.

Использовать транзакцию при атомарной смене метки удаления, перемещении закладки или миграции структуры.

Миграции должны быть идемпотентными: повторный запуск не теряет строки и не дублирует ключи.

Версия форк-схемы живёт в `tele_kv`; не менять stock `LAST_DB_VERSION` и не использовать stock migration number.

Добавлять индексы по реальным запросам (account/dialog/message/time), не строить полные сканы на каждом открытии чата.

Фоновое чтение/запись не трогает views; результат публиковать на UI через `AndroidUtilities.runOnUIThread` после проверки жизненного цикла fragment.

При ошибке записи логировать тип операции и безопасный контекст без текста сообщений/секретных данных.

Не выводить тела сообщений, подписи, usernames, file paths и содержимое закладок в logcat.

## Потоки, аккаунты и recycling

SQLite операции выполняются через DB очередь, не из `onBindViewHolder` и не из `ChatMessageCell.draw`.

Соблюдать `currentAccount` при чтении конфигурации, helper singleton и DB query.

Callback может прийти после закрытия fragment: не обращаться к старому view; перепроверить lifecycle и account.

Все визуальные эффекты применять на main thread и повторно на bind после recycling.

Не хранить state только в view fields; это теряется при пересоздании activity и смене темы.

При одновременном удалении/rollback/expiry использовать транзакции и условные обновления по первичному ключу.

При выключенной функции не менять сеть, серверные списки, read state и результаты стокового кэша.

## Privacy и хранение

Все данные удалённых сообщений, bookmarks и read history остаются локально в tele DB.

Не экспортировать содержимое сообщений, bookmarks и локальные идентификаторы в tele server.

Settings export/import — пользовательское действие и должно следовать текущей политике телеметрии/экспорта; приватные записи не включать без отдельного решения.

Ошибки logcat не должны содержать тела сообщений, полные file paths или персональные данные.

Удаление базы приложения уничтожает эти данные; текст настроек не обещает cloud backup.

## Тестирование функций по отдельности

Все пункты ниже — ручные проверки на реальном debug build; compile-only не закрывает acceptance.

Проверить каждую функцию включённой и выключенной; по умолчанию выключенное поведение должно быть стоковым.

### Deleted retention и media

1. Включить 0068 и установить срок forever.
2. Получить удаление сообщения другим устройством; проверить метку и содержимое.
3. Закрыть процесс, запустить снова; сообщение и история правок присутствуют.
4. Переключить срок 1 день; использовать управляемую тестовую дату/фикстуру, не ждать сутки.
5. Проверить истёкшую запись и неистёкшую запись после sweep.
6. Повторить для 7 и 30 дней и навсегда.
7. Сохранить сообщение с медиа, очистить штатный Telegram cache; открыть kept media повторно.
8. Удалить архивную запись и убедиться, что файл вновь доступен к очистке.
9. Повторить с edit history после удаления исходного сообщения.

### Rollback

1. Запустить удаление своего сообщения и имитировать FLOOD_WAIT/сетевой сбой на тестовой сети.
2. Проверить, что сообщение снова выглядит обычным и не остаётся deleted в базе после рестарта.
3. Повторить с жёсткой серверной ошибкой.
4. Успешное удаление не должно откатываться.
5. Закрыть чат до callback; убедиться в корректной модели и отсутствии crash.

### Удалённые диалоги, топики, массовое удаление

1. Тестовый супергрупповой чат: удалить диалог/выйти, проверить локальную запись после рестарта.
2. Форум: отдельно проверить удаление топика и родительского диалога.
3. Проверить принудительное удаление с сервера и ручную очистку архива.
4. В тестовом чате выбрать «удалить все мои сообщения», подтвердить точный scope.
5. Проверить чужие сообщения остаются, kept-deleted пропускаются, прогресс и cancel работают.
6. Получить FLOOD_WAIT; убедиться, что запросы не повторяются чаще разрешённого времени.

### Bookmarks и return point

1. На сообщении создать закладку через меню; перезапустить, открыть список и перейти к сообщению.
2. Снять закладку из меню; проверить после повторного входа.
3. Проверить несколько аккаунтов и два чата с одинаковым message id.
4. Проверить topic id, Saved Messages, удалённое сообщение и недоступный peer.
5. Включить точку возврата, прочитать место, закрыть чат, открыть снова; позиция восстановлена без неожиданного сетевого mark-as-read.
6. Выключить оба переключателя: интерфейс и поведение как stock.

### Read time

1. Включить 0147 и получить outbox read update со второго клиента.
2. Проверить время в `MessageSeenView`, переживание рестарта и повторного update.
3. Выключить переключатель: новое значение не появляется и стоковый seen UI сохранён.
4. Проверить несколько аккаунтов, каналы/группы и случаи, где read update не доступен.

### GIF/sticker limits

1. Добавить GIF/стикеры до серверного лимита и сверх него.
2. Перезапустить; проверить локальные сверхлимитные элементы и стабильный merge.
3. Проверить обычный серверный список на другом клиенте: локальные записи туда не ушли.
4. Отправить сохранённый GIF после устаревания file_reference; проверить штатный refresh и обработку ошибки.
5. Удалить локальную запись и проверить, что серверное избранное не удалилось случайно.
6. Выключить фичу и сравнить со стоковыми лимитами.

## Logcat и диагностика

Фильтровать `adb logcat` по tag helper/TeleDatabaseHelper и по SQLite exception, не включать текст сообщений.

Ожидать отсутствие SQL на main thread и отсутствие `database locked` при быстрых add/remove.

При миграции фиксировать номер fork schema и факт завершения, не печатать строки таблиц.

Для сетевого удаления логировать класс ошибки и operation id, но не message body.

Проверить отсутствие повторных callback-побочных эффектов и повторной отправки delete request.

При каждом crash собирать короткий stack trace с account index и экраном, исключив PII.

## Миграции и обратная совместимость

Не сбрасывать данные 0068/0069 при добавлении новых таблиц.

Сначала создать новые таблицы/индексы, затем мигрировать поля/версии в транзакции, в конце фиксировать `tele_kv` schema version.

При сбое миграции оставить старый version marker и безопасно повторить на следующем старте.

Не полагаться на обновление всех пользователей с чистой базой; проверить базу с данными предыдущего релиза.

Если формат `tele_kv` JSON меняется, поддержать чтение старого формата и однократную миграцию с тестовой копией.

Не удалять старые колонки/таблицы до доказанного отсутствия читателей и отдельного решения.

Учесть несколько аккаунтов и одноразовые старые/пустые базы.

## Features.md и документация

Для каждой user-facing функции пачки обновить `main/features.md` отдельной строкой на странице с её переключателем.

Текст на английском, одно простое предложение: назначение, место настройки, default off, ссылка на Android patch file и текущий desktop номер.

Deleted settings относятся к `your data`; bookmarks/read-time/GIF settings требуют выбора страницы после просмотра текущей структуры.

Не выдумывать имена будущих patch files: обновлять links при экспорте соответствующего commit.

PATCHLIST менять статусы только по факту: todo → wip → queued → built → done.
